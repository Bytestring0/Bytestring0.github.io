# Mizuki 文章专属前端

目标：用户写完 md → agent 读文并确认设计 → 实现该文专属页面 → 用户自己 run dev → 根据反馈修改同一份设计 → 满意后用户 build / deploy。

## 先看内容，再确认

1. 定位当前仓库（`package.json` 的 name 为 mizuki，存在 `src/content.config.ts`），明确目标 md/mdx；未指定时只询问目标，不扫描所有文章。完整读目标文章、运行 `pnpm article-design status "文章路径"`，有设计就读该 `.astro` 和 `.json` 的 plan。了解文体、结构、关键素材和现有主题，按需读 `src/styles/variables.styl`，不用重读整个项目。
2. **初次创作或彻底改版必须先向用户确认，收到回复才生成。** 用一小段说清贴合文章的视觉构思、排版/阅读顺序是否改变、动画与交互、阅读负担及是否增加 AI 导读。推荐一个方向，必要时给一个差异明显的备选；不要堆方案或先实现再让用户确认。用户可以提问，agent 可提出内容建议，但建议不自动写回原文。本轮已明确认可的风格可直接采用；已有设计的明确小幅修改无需再走完整确认。
3. 默认控制篇幅和动效，继承主题色；用户确认需要复杂动画时可以充分实现。**assets 中的 Astro 模板只是接口与结构参考，不是成品，不能直接复用模板布局交付。** 根据这篇文章确定布局和阅读机制，再组合现有组件。

## 创作的自由与边界

- 专属 `.astro` **接管整个页面**，包括导航、目录、正文、评论和页脚，不套原来的网格或文章卡片。通过 `PageShell` 和提供的导航、目录、评论等组件接口组合完整 HTML，自由决定位置、尺寸、样式，也可重做导航 UI 并调用主题接口。允许自由的文字排版、段落/章节顺序、分屏、滚动叙事、图形和复杂动画。保留导航、原文锚点、主题切换、评论和页面切换功能；不要把新页面放进 iframe 或另建脱离博客的独立 HTML。
- 原 md/mdx 是内容的唯一来源。**不得改写原句、删节、纠错或把手抄正文替代原文**；除用户授权的 frontmatter `create` 开关外不编辑原文。可通过 `article.blocks` 重排呈现，原文块各出现一次。允许动效用的字词 span，仍需保持逐字内容。代码、公式、表格、媒体和链接用 Astro 已渲染的原始块。
- 允许在开头加简短导读，或在边缘/文末加少量补充。清楚标为“AI 导读”/“AI 补充”，视觉上次于正文；避免装成作者观点，不重复大段原文，不给补充添加会混入目录的原文标题 id。
- 用内容本身形成特色：一篇文章选择适合它的阅读机制或视觉线索。避免套路化渐变大标题、无关英文标签、每段一张卡、装饰性统计、无意义图标、空泛总结。不要求每篇都与所有旧文完全不同，也不用遍历旧文证明创新。
- 继承 `--primary`、`--card-bg`、`--line-divider` 等主题变量；禁止大面积换色或覆盖全站主题。移动端、暗色和减少动态偏好要可读；复杂动画可降级为静态阅读或提供停止控制。不能要求看完动画才能读文，不能滚动劫持。重排时按**实际 DOM 阅读顺序**编排，不仅靠 CSS order 改视觉顺序。

## 实现与复用

布局偏好：保留全站原生纵向滚动条；宽表格、公式和长目录使用局部可见滚动条，不裁掉内容。目录优先在正文范围内 `sticky` 跟随，避免 `fixed` 悬浮遮挡，手机可折叠或回到文档流。正文可以更宽，尤其技术文章；先保证正文宽度，再给目录和装饰分配空间，不层层套 max-width/padding 挤成小栏。

开始实现先读 [操作步骤与 STA 复盘](references/working-method.md)，按其中的短流程完成；接口不清楚时查 [references/implementation.md](references/implementation.md)，不要反复重读全套文件。

- `create` 缺失/false：原版。true 且无设计：原版回退，agent 确认后才创作。dev/build/访问不会调用 AI。
- 确认后设 `create: true`，运行 `pnpm article-design init "文章路径" editorial|lab|story` 建立绑定和接口骨架；命令复制的模板仅为参考，按确认方案改写布局后再交付。复用博客组件，无须从零重搭基础设施；不要手写假的 key/sourceHash。
- 文件已存在就修改同一个 `.astro`，保留清单与确认方案。`init` 不覆盖。正文指纹变化只意味着需要适配，**不是重新生成许可**；不要删除文件重新跑 init，也不要每次打开 agent、dev 或 build 自动重做。
- Markdown 被删除后，下次 Astro 构建会清理其绑定的 `.astro` / `.json`。关闭 create、草稿、内容变化不会清理；改名/移动文章时先迁移绑定，再构建。`pnpm article-design prune` 可只读预览。
- 将确认方向、动效、顺序调整、AI 增补和后续偏好简要写入同名 `.json` 的 `plan`，作为跨会话记忆。适配完原文变化后才运行 `accept-source`。改名/移动文章时参考实现文档迁移绑定。
- **不要过度思考、过度实现。** 默认单 agent、一个方向、一次完整实现；确认后直接动手，不反复推演方案，不堆装饰/辅助面板/交互，不做无关重构。先完成用户要的效果，集中做一次针对性验收、集中修复实际失败，尽量一次解决；检查通过就交付，不为臆测风险不断加功能、加测试或重复构建。复杂效果只在文章需要或用户明确要求时做，不能借节省 token 擅自缩水。

## 交付前

生成或修改页面后，先运行 `pnpm article-design lint "文章路径"` 排除占位符、错误 key、无效指纹等，再运行 `pnpm article-design:check "文章路径" --route /文章地址/ --full-page`。它临时启动 dev 后关闭，输出截图、JSON 和 HTML 报告；用法和限制见 [验收工具](references/validation.md)。**打开并查看桌面和手机截图**，修复实际报错，核实警告；滚动揭示页面须实际滚动检查各章，不能只看首屏截图与退出码。再验证导航菜单、目录跳转、评论加载及页面特有交互。用户自己 run dev；不常驻服务。明确已检查和未验证项，不把编译通过当作页面完成。

用户决定满意与否；继续修改同一份设计。**不得自行 deploy、push 或触发发布。** 用户说满意后可告知 build/deploy 命令；只有明确要求执行时才代为执行。构建验证使用无同步/无发布的 `pnpm exec astro build`，避免误触内容同步和网络更新脚本。
