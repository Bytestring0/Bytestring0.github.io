# RAY PV：程序把记忆变成图像

状态：供本轮审阅的脚本。现有 PV 的场景实现不能作为本脚本已经完成的证明。先确定下面的因果关系、分镜和音乐落点，再修改动画。

## 1. 故事与最后一帧

一个已经编译好的 CPU 软件渲染程序，读取保存在内存中的星点与彗星轨迹，计算覆盖范围、折射、边缘亮度及颜色，写出完整图像，最后呈现在一台 OLED 显示器上。

最后的图像是有构图的作品：玻璃般透明的彗星位于右上，弯曲的尾迹从左下延伸过来；背景星点可以透过核心看见，靠折射位移和边缘反光辨认其形体；少量星点在左下构成 RAY。这个结果从开场的输入数据中产生，不临时换成另一张无关图像。

情绪线：记忆被保留 → 无形的数据被理解和计算 → 走过一次错误的预测 → 每个局部结果汇合 → 看不见的程序成为看得见的图像。CPU 的运行是叙事本身。

全片无人物。字幕只使用用户提供的日文歌词。画面中的技术文字只在有助于理解当前动作时出现。

## 2. 贯穿全片的程序

选择带 CPU、共享内存和显示控制器的通用 SoC 作为示意对象，不假冒任何具体商业芯片的真实版图。CPU 完成软件渲染，显示控制器负责输出图像。

源代码是人类阅读的表达；开场运行的是已编译程序。屏幕不是程序存储器，不能把编辑器里的字沿显示器线缆送进 CPU。

```text
编辑器中的源代码 ──编译/加载（开场交代）──> 内存中的可执行程序
                                                │
指令路径：内存 → 指令缓存 → 取指/译码 → 重命名/派发 → 等待操作数 → 执行 → 退休
数据路径：内存中的星点/轨迹 → 数据缓存 → 加载单元 → 物理寄存器 → 执行单元
结果路径：正确路径上的存储 → 存储缓冲/缓存一致性 → 内存中的后缓冲图像
显示路径：完成整帧 → 呈现请求/必要的交接 → 扫描输出缓冲 → 显示控制器 → 显示链路 → OLED
```

图中的退休、存储可见、显示呈现是不同事件，不能合并成“ALU 算完就直接点亮显示器”。演出中省略具体操作系统和窗口合成器细节，但保留渲染缓冲与扫描输出缓冲之间的交接。

程序逻辑采用下面的伪代码。实际实现必须提供与其一致的计算记录；伪代码不冒充某架构的机器码。

```text
back = renderStars(memory.stars)
for tile in tiles(back):
    for P4 in groupsOfFourPixels(tile):
        background4 = load4(back, P4)
        distance4, normal4 = distanceToTrail(P4, memory.path)
        coverage4 = coverage(distance4)

        if all(coverage4 == 0):
            store4(back, P4, background4)
            continue

        through4 = sampleStars(P4 + normal4 * refraction, memory.stars)
        glass4 = through4 + edgeReflection(distance4)
        color4 = mix(background4, glass4, coverage4)
        store4(back, P4, color4)

presentCompletedFrame(back)
```

跟踪对象是一组四个相邻像素，其中轨迹边缘的像素 P 以细小的琥珀色标记识别。这个标记是叙事标识，不是发光粒子。程序地址、输入轨迹、寄存器值、分支条件、颜色和输出位置必须能对照同一份记录。此前的纯背景像素组已由相同循环处理；当前重点跟踪的 P4 要到正确着色、退休和存储之后才进入帧缓冲，不能在副歌开始时提前宣告这个像素已经完成。

四个 SIMD 通道处理四个像素，不能画成四颗 CPU，也不能把四个完全依赖的步骤说成同时执行。影片先放大一组像素的过程，随后呈现相同循环处理其余图块。

## 3. 物理空间与尺度

三种画面空间有清楚的边界：现实中的工作站；芯片内部的物理结构；解释数据关系的图解空间。用匹配剪辑衔接，不把抽象的像素矩阵伪装成 RAM 的实际排列。

物理镜头的放大顺序固定：CPU 封装 → 硅片 → 某核心的执行单元 → 标准单元 → 晶体管。每次跨尺度都先给出所在区域，再放大进去；退出时回到同一位置。不能把一个巨大晶体管摆在缓存、寄存器文件旁边当建筑。

晶体管镜头采用明确的 FinFET 示意：鳍位于硅衬底上，源漏沿鳍的纵向分居两端，栅跨过鳍并包覆沟道的顶面和侧面，栅与沟道之间保留绝缘层；上方接触和金属连线连接到标准单元。根据 Intel 的 Tri-Gate 结构图校核几何关系。[结构参考](https://download.intel.com/newsroom/kits/22nm/pdfs/22nm-Details_Presentation.pdf)

微观段只解释一次清楚的 CMOS 反相器动作：输入 A 从 0 变 1，pMOS 关断、nMOS 导通，输出 Y 从 1 变 0。先在标准单元尺度看见输入/输出，再看栅控制沟道，最后回到连线上的结果。它只是执行电路中的一个逻辑动作，不能声称一只晶体管完成整次浮点计算。

不使用示波器、正弦曲线、装饰性同心波。状态变化通过栅电压标识、沟道导通/截止、输出节点电平和寄存器接收来表达。

## 4. 音乐与动作的统一规则

音源为项目中的 ray.mp3，时长约 281.152 秒。现有频谱分析估计速度为 132 BPM，即一拍约 0.4545 秒；四拍为 1.818 秒、八拍为 3.636 秒。拍号和每段第一拍仍须在制作时对照录音校核，不能把估算的全曲相位直接当作所有剪辑点。

歌词入句、音乐瞬态、镜头启动、动作完成分别标记。字幕跟人声；撞击、合拢、转交、切镜的完成时刻跟实际音乐事件；镜头应提前加速，到事件时到达目标，不在事件发生后才开始移动。

下面的毫秒数取自当前录音的频谱瞬态检测，是待逐段听辨的候选点，不将其全部声称为底鼓或军鼓。已有算法没有完成可靠的鼓、人声与其他乐器分离。

节奏编排：

- 主歌以八拍动作句为主：建立位置 → 预备 → 加速 → 到达，保留阅读和理解时间。
- 副歌以四拍动作句为主，穿插二拍细节镜头；一次动作对应一次数据状态改变。
- 间奏允许半拍/一拍的短插镜，但必须沿同一结果路径推进。
- 同一瞬态最多安排一个主要事件。背景、电平、字幕和相机不同时闪烁。
- 不用整颗芯片缩放或全屏亮度脉冲代替踩点。CPU 的硬件时钟与歌曲拍速无关，微观过程经过电影式时间放大。

## 7. 技术因果核对

- 预测可以提前发生；误预测必须等实际分支在执行端被判定后才能发现。错误路径上的年轻微操作被撤销，已经退休的正确结果不被倒放或清空。[Intel 执行与退休说明](https://www.intel.com/content/www/us/en/docs/vtune-profiler/user-guide/2026-0/instructions-retired-event.html)
- 一条指令可对应多个微操作。重命名、调度、执行完成和退休各有作用；依赖没有满足时不能让该操作提前得到结果。
- 透明彗星的形体由输入轨迹和计算决定，最后的像素必须能回溯到相同计算记录。不得插入无来源的分形球或现成图片。
- 后缓冲写完后才呈现；显示控制器扫描缓冲并送往显示器。CPU 核心和显示控制器不得合并成一个单元。[KMS 显示缓冲与扫描输出接口](https://www.kernel.org/doc/html/latest/gpu/drm-kms.html)
- 原始机器码、商业芯片布局、晶体管连接图若没有实际来源，就采用明确的概念表达，不拼接虚构的字节或假装精确复刻。

## 8. 修改动画前的验收门槛

本轮用户要求开始实现并提高效率；晶体管只保留60.263–63.903秒的主歌插镜，高潮保持结果接力和图像形成。

可检查的材料包括：最终图像与输入轨迹；像素 P 的实际计算记录（输入、距离、覆盖率、分支、颜色、写入位置）；带音乐的低精度分镜预演。

分镜预演只验故事、镜头方向和音乐落点。确认所有结果都有前因，晶体管的进入/退出位置一致，主副歌与间奏的密度有差异后，才制作精细材质、光照和转场。精美效果不能用来遮盖因果缺口。

最终逐项核对：字幕与人声；主要动作与局部音乐事件；暂停/跳转后的状态一致；桌面和手机可辨识；最后显示的确实是该程序的输出。本脚本本身不等于完成以上验证。
